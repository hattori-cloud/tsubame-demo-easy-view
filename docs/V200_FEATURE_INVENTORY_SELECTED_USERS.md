# V200 機能棚卸し — 指定利用者型への整理

更新日: 2026-09-26

## 前提

本番仕様は以下とする。

- 全社員は管理対象
- システムへログインするのは会社が指定した管理者・担当者のみ
- 本番利用者は full / scoped
- 社内LAN / 社内Wi-Fiのみ利用可
- 自宅回線・モバイル回線・テザリング・社外Wi-Fi・社外VPNは不可
- scoped利用者は「事業所 × 部署 × 機能 × view/edit」で制限
- 一般社員向け self 利用は本番対象外

この前提で、現在のV200機能を「残す」「統合する」「削除候補」に整理する。

---

## 2026-09-26 実装済み

- デモ／本番候補とも一般社員向け `self`、自分画面、掲示・申請の見える導線を除去。
- `/applications` / `/notices` / `/confirmations` 系は中央routerから登録解除し、全環境で404。
- 上記3系統の旧APIハンドラと専用workflow CRUDコードも削除済み。
- `handoffs` は管理者間引継ぎとして独立して維持。
- 新規本番DBの利用者ロールは `full / scoped` のみ。指定利用者はMFA必須。
- 既存DBの旧 `self` 利用者は削除せず、user IDを保持したままセッション失効・scope/feature権限解除・`scoped + suspended` 化し監査記録を残す。
- `applications / notices / notice_reads / confirmations / confirmation_responses` テーブルはrollback・過去監査互換のため当面保持し、物理DROPは別監査後に判断する。

| 勤務集計 | 残す | 拘束時間・残業等を管理者が確認 |
| 事故 | 残す | タクシー業務の安全管理中心機能 |

## 2. 統合する — 機能は残すが独立画面を減らす

| 現在の機能/画面 | 統合先 | 整理方針 |
|---|---|---|
| 事故・苦情・ヒヤリの個別上位メニュー | **運行・安全** | API/DBは分けたまま、利用者の入口だけ1つにまとめる |
| 資格・書類の独立上位メニュー | **社員詳細 + 期限・勤務** | 資格情報は社員詳細、期限確認は期限画面、原本操作は詳細内 |
| 勤務取込の独立上位メニュー | **期限・勤務 または 管理** | 普段見る画面から分離し、取込担当だけに見せる |
| 利用者管理 | **管理** | 権限・アカウント・MFAを管理画面に集約 |
| 監査ログ | **管理** | 通常利用者の上位メニューには出さない |
| 原本storage / backup状態 | **管理** | システム管理者だけが確認 |
| 安全指導・教育 | **運行・安全 + 社員詳細** | 独立画面を増やさず、対象社員/安全案件から開く |
| 貸与品 | **社員詳細 + 管理** | 社員に紐づく記録として扱う。独立上位メニューは不要 |
| ゴールド/英語/観光認定 | **社員詳細** | 認定状態と履歴を社員詳細へ集約 |
| 引継ぎ一覧 | **ホーム + 対象案件詳細** | 新しい引継ぎはホーム、履歴は事故等の詳細から確認 |
| 注目社員 | **ホームの補助機能に限定** | 残す場合も独立機能化しない。優先対応/検索が十分なら将来削除可 |
| 休職・退職手続 | **社員詳細** | 対象社員のtransitionとして扱う |
| 下書き | **事故/苦情/ヒヤリ入力内** | 独立メニュー化しない |

## 3. 削除候補 — 新仕様では役割が薄い

| 機能 | 削除候補理由 | 影響 |
|---|---|---|
| **自分** 画面 | 一般社員がログインしない | demoの本人画面、self-only UIを除去 |
| **self権限** の本番利用 | 指定利用者型と矛盾 | 本番loginはすでに禁止。互換コードは段階的整理 |
| **一般社員向けホーム** | 本人利用がない | 自分の勤務/期限/申請の表示を削除 |
| **掲示** | 全社員向け配信先がなくなる | notices API/UI/既読管理を本番対象外へ |
| **掲示の既読管理** | 掲示を外すため不要 | notice_readsを新規運用しない |
| **一斉確認** | 全社員に回答させる設計が不要 | confirmations / confirmation_responsesを本番対象外へ |
| **本人変更申請** | 一般社員がシステムへ入らない | applications UI/APIを本番対象外へ |
| **掲示・申請 上位メニュー** | 上記3機能の役割が消える | メニュー自体を削除 |
| **全体検索の「掲示」「申請」対象** | 対象機能を外すため不要 | 検索対象から削除 |
| **一般社員向けMFA enrollment UI** | 一般社員アカウントを発行しない | 管理者/担当者用MFAだけ残す |
| **一般社員向け変更申請導線** | 本人画面を廃止 | self-onlyボタン・申請案内を削除 |

### 削除候補だが、すぐDB DROPしない

既存の以下テーブルは、画面・API実装から外しても直ちに物理削除しない。

- applications
- notices
- notice_reads
- confirmations
- confirmation_responses

理由:
- 監査固定点との互換性
- 移行/rollback
- 既存テスト
- 過去データが存在する可能性
- 60%以降のCODEX監査差分を小さく保つ

まず本番UI/権限から無効化し、利用しないことを確認後にschema cleanupを別migrationで判断する。

追加の防御:
- production runtime DB roleから applications / notices / notice_reads / confirmations / confirmation_responses の SELECT/INSERT/UPDATE/DELETE を剥奪する。
- handoffs は管理者間引継ぎとしてruntime accessを維持する。
- 旧テーブルは物理削除せず、rollback / audit互換用として当面保持する。

## 4. 引継ぎは「掲示」と分離する

旧設計では以下が同じfeature permissionに束ねられていた。

`notices / confirmations / handoffs / applications -> notices_workflow`

現在は handoffs を独立済みとし、旧3系統はrouter・runtimeコードから除去済み。

### 新しい方針

- notices: 本番無効
- confirmations: 本番無効
- applications: 本番無効
- **handoffs: 残す**

そのため、permission featureを将来的に:

`notices_workflow`

から、

`handoffs`

へ分離する。

scoped利用者は、引継ぎを必要とする役割にだけ `view/edit` を付与する。

## 4.5 薄い機能を作らない判断基準

上位メニューや独立画面は「機能が存在するから」ではなく、実務として一つの仕事が完結するかで判断する。

独立させない条件:
- 単独で処理が完結せず、結局別画面へ移動するだけ
- 同じ入口が2か所以上あり、利用者がどちらを押すか迷う
- 月数回以下の操作なのに常時上位メニューを占有する
- 一覧を見るだけで、対象社員・号車・案件へ進めない
- 分析結果を見ても実務画面へ戻れない
- 廃止済み機能の件数・品質警告・タスクだけが残る

独立させる条件:
- 日常的に開く
- その画面内で主要な業務が完結する
- 前後の業務へ直接移動できる
- 権限の意味が明確
- 他画面と重複しない

### 2026-09-26 実装整理

- **引継ぎ・安全指導**: 独立画面ではなく「運行・安全」へ統合。未確認引継ぎと次回安全指導を事故・苦情・ヒヤリと同じ流れで確認する。
- **勤務取込**: 「期限・勤務」を正規入口とし、「管理」からの重複入口を削除。
- **利用者・権限 / 監査ログ**: 「管理」へ集約。権限変更後の追跡まで同じ領域で確認する。
- **安全教育・貸与品**: 社員詳細へ統合。独立上位メニューにしない。
- **分析**: 削除しない。デモでは会社全体・安全・人事・総務を横断するため独立領域として役割がある。本番UIでは分析結果から事故・苦情・ヒヤリへ直接戻れる導線を追加。
- **ホーム**: 横断検索を追加し、社員・号車・事故・苦情・ヒヤリを権限範囲内で一度に検索できる起点へ変更。
- **社員 ↔ 安全案件 ↔ 車両**: 相互リンクを追加し、社員番号や号車を再入力せず辿れるようにする。
- **旧申請・掲示・一斉確認**: 今日の処理キュー、管理KPI、データ品質チェックからも除外し、廃止済み機能が現役業務へ再浮上しないよう整理。

### 2026-09-26 便利さ・実運用スケール改善

- **社員詳細を業務ハブ化**: 要対応期限、担当号車、事故・苦情・ヒヤリ件数、安全教育、貸与品、資格・書類へ社員詳細から直接移動できる。
- **期限 → 対象へ直行**: 期限一覧から社員詳細、車検・整備期限から該当号車へ直接移動できる。
- **車両担当変更を本番UI化**: 主担当・追加担当・車両区分を専用APIで更新。310人規模を考慮し、巨大プルダウンではなく社員番号または氏名検索で特定する。
- **100人候補上限を廃止**: 事故・苦情・ヒヤリ・安全指導・新規車両登録で、先頭100人だけが候補になる設計を廃止。権限範囲内をサーバー検索して対象社員を特定する。
- **一覧50件止まりを廃止**: 社員、期限、事故、苦情、ヒヤリ、車両、資格対象社員、利用者、監査ログにページ送りを追加。5年運用でも全件へ辿れる。
- **検索状態を見える化**: 社員詳細から履歴へ移動した場合など、内部の絞り込み条件を検索欄にも表示。別メニューへ移動時は古い検索条件をクリアする。
- **安全案件 ⇄ 社員 ⇄ 号車**: 再検索せず相互に辿れる導線を維持する。
- **規模前提**: 現社員約310名、ヒヤリ年間約400件、事故月約20件、退職者・監査履歴を複数年保持する前提でUIを設計する。

### 残る厚みの差

デモの「分析」は会社全体・安全・人事・総務まで横断しているため独立上位領域として成立している。一方、本番APIモードの分析は現時点では安全分析が中心である。
そのため、本番側で分析を上位領域として維持する場合は、次段階で人事・総務・全社横断のサーバー集計を追加し、デモと同等の役割へ近づける。安全分析だけのまま独立メニューを固定しない。

### 2026-09-26 本番分析の厚み強化

本番側の「分析」を安全分析だけの薄い画面から、管理判断に使える横断分析へ拡張した。

- **現在人員**: 在籍、休職、退職予定、直近12か月入社を現在所属ベースで集計。
- **期限**: 免許・健康診断・適性診断の60日以内／超過人数を集計。
- **資格・書類**: 資格期限超過、書類の確認・差替・保存状態の要確認件数を集計。
- **教育・貸与品**: 未完了教育の期限超過、貸与品返却超過を集計。
- **勤務**: 最新月の残業60時間以上人数と平均残業時間を集計。
- **車両**: 車検超過、車検60日以内、整備予定超過を集計。
- **安全**: 事故・苦情・ヒヤリ、未完了比率、高リスク比率、修理費、月別推移、記録時所属別比較を維持。
- **横断確認**: 「直近12か月入社 × 選択期間の安全記録」「安全記録 × 現在の期限対応」「退職予定 × 未返却貸与品」を人数だけで表示。
- **業務へ戻る**: 分析から社員、期限、資格・書類、勤務、車両、運行・安全へ直接移動可能。
- **権限分離**: safety_analysis 権限だけでは、社員・期限・資格・貸与品・勤務・車両の集計を返さない。各feature permissionがある集計だけ返す。
- **評価用途禁止**: 個人順位、危険人物判定、退職予測、評価スコアは作らない。

集計基準を混同しない:
- 人員・期限・資格・教育・貸与品・勤務・車両は **現在所属** で「今の業務」を見る。
- 事故・苦情・ヒヤリの部署分析は **記録時所属snapshot** で「過去の発生状況」を見る。
- 現在人員を分母にした安全の100人あたり値は、引き続き「参考値」であり真の発生率とは扱わない。

実SQLはGitHub Actionsで空のPostgreSQLへ実行し、feature isolationも同じCIで検証する。
既存安全分析で実DB実行時に発見した月別集計alias `month` のPostgreSQL構文問題も修正し、再発テストを追加した。

### 2026-09-26 入力・更新の再入力削減

本番UIの便利さを「画面数」ではなく、再検索・再入力・行き止まりを減らす方向で強化した。

- **社員詳細 → 新規安全登録**: この社員で事故・苦情・ヒヤリ・安全指導を登録できる。社員番号・氏名を再入力しない。
- **担当号車の引継ぎ**: 対象社員の現在担当号車が1台だけなら、事故・ヒヤリ登録へ号車を初期入力する。複数号車の場合は誤選択防止のため自動決定しない。
- **車両詳細 → 新規安全登録**: この号車で事故・ヒヤリを開始できる。主担当が特定できる場合は社員も引き継ぐ。
- **閲覧専用車両でも安全登録可**: 車両編集権限がなくても、事故・ヒヤリ編集権限があれば号車を引き継いで登録できる。車両編集権限は付与しない。
- **期限 → 該当作業へ直行**: 免許等は社員、資格・書類は資格画面、教育・貸与品は該当レコード、車検・整備は号車を直接開く。
- **資格・既存書類の更新**: 期限画面から到達した後に行き止まりにならないよう、既存資格と書類メタデータをversion付きで更新可能にした。
- **期限クイックフィルター**: 要対応（超過〜30日）、超過、本日、30日以内、31〜60日、60日全体をワンタッチで切替。表示条件と件数ラベルを一致させた。
- **社員番号変更・異動/在籍状態**: 全社管理者の社員詳細から専用APIを実行できる。通常プロフィールPATCHには混ぜない。
- **重要変更の保護**: 社員番号変更・異動/休職/退職は理由必須、MFA、If-Match、監査・履歴を維持する。
- **社員履歴を見える化**: 社員番号変更履歴と異動・在籍状態履歴を社員詳細へ表示し、「変更 → 履歴確認」を同じ画面で完結させる。

設計ルール:
1. 画面遷移元で既に確定している社員・号車は、次画面で再入力させない。
2. ただし候補が複数ある場合は勝手に決めず、利用者に選ばせる。
3. 「更新してください」と表示する期限は、実際に更新できる画面までつなぐ。
4. 権限の便利さを理由に別機能の編集権限を広げない。
5. 社員番号・所属・在籍状態など履歴性が重要な変更は通常編集に混ぜず、専用操作を使う。

### 2026-09-26 引継ぎを案件処理の線へ統合

引継ぎを「未確認一覧を見るだけ」の薄い機能から、事故・苦情・ヒヤリの処理線へ統合した。

- 事故・苦情の詳細、ヒヤリ一覧から引継ぎを作成できる。
- 引継ぎ先の内部利用者IDは入力させない。
- 対象社員の現在所属を担当できる有効な全社管理者／範囲指定管理者だけを候補表示する。
- 自分自身は引継ぎ先候補から除外する。
- 引継ぎ内容は必須とし、「相手が次に何を確認・対応するか」を記録する。
- 受け手のホーム／運行・安全には未確認引継ぎを表示し、元の事故・苦情・ヒヤリへ直接戻れる。
- 確認済み操作は指定された受け手本人だけが実行できる既存制約を維持する。
- 事故・苦情が閲覧のみでも、handoffs編集権限がある場合は「引継ぎ」だけ実行可能。事故・苦情の編集権限は広げない。

### 2026-09-26 タクシー勤務区分と基本固定車

タクシー乗務員の勤務と車両は、迷わないように別概念として管理する。

**勤務区分の正式表示**
- 日勤
- 夜勤
- 隔勤
- H勤

過去データの「隔日勤務」「隔日」は画面では「隔勤」、「午後から隔日勤務」「H勤務」は「H勤」と読み替えて表示する。
新規登録・今後の編集候補は上記4区分に統一する。

**基本的な所属の流れ**
- 入社時: 訓練課 + 日勤が基本
- 隔勤 / H勤: タクシー1課・2課が基本
- 日勤 / 夜勤: タクシー3課が基本
- これは強制ルールではない。異なる組み合わせは警告だけ出し、管理者が例外として登録できる。
- 全社社員台帳なので、DB側で全社員へ「日勤」を自動設定しない。

**所属表示の整理**
- 事業所と所属部署を正式な組織表示として使う。
- `taxi_section` は互換用フィールドとしてDBに残すが、通常の社員登録・編集・詳細画面には出さない。
- タクシー1課/2課/3課は `department`（所属部署）で扱い、同じ意味の二重入力をさせない。

**車両は勤務区分と別管理**
- 「基本固定車」は勤務区分から推測しない。
- 日勤、夜勤、隔勤、H勤のどの勤務区分でも基本固定車を持てる。
- 内部の assignment_mode=`dedicated` は画面上「基本固定車」と表示する。
- 基本固定車は「普段の基準車」であり絶対固定ではない。
- 事故、故障、修理、代車等で別号車に乗ることを許容する。
- 別号車に乗っただけでは基本固定車の設定を自動変更しない。

**事故・ヒヤリでの号車**
- 基本固定車がその社員に1台だけ明示されている場合だけ、事故・ヒヤリ登録の号車へ初期表示する。
- 初期表示された号車は常に変更可能。
- 保存するのは「その時実際に乗っていた号車」。
- 基本固定車がない、または複数ある場合は自動入力しない。

**履歴**
- 勤務区分変更は profile_update の履歴から社員詳細に表示する。
- 所属 / 在籍状態変更、社員番号変更とは別履歴として見せる。

### 業務の線

`ホーム（検索・今日の確認） → 社員 / 号車 / 案件 → 処理 → 履歴 → 分析 → 対象業務へ戻る`

上記の流れから外れる機能は、原則として上位メニュー化せず、対象社員・案件・管理画面の中へ統合する。

## 6. 削減してはいけないもの

画面を簡単にするために、以下のサーバー側保護は削減しない。

- scope authorization
- feature view/edit authorization
- MFA
- session invalidation
- internal network restriction
- audit/history
- optimistic concurrency
- work-import preflight/version/rollback
- original quarantine/malware/SHA
- encrypted secondary backup
- restore verification
- employee number history
- historical office/department snapshots

「見た目を簡単にする」と「安全機能を消す」は分けて扱う。

## 7. 実装順序

1. handoffsを `notices_workflow` から独立
2. production/demoメニューから self / 掲示・申請を非表示
3. 全体検索から掲示・申請を削除
4. 一般社員向けself UIを削除
5. notices / confirmations / applications APIを中央routerから登録解除し全環境で無効化
6. 権限presetから `notices_workflow` を削除し `handoffs` へ置換
7. 利用者管理UIを7メニュー構成へ合わせる
8. CI / scope / permission regression
9. 画面確認
10. 旧テーブルの物理削除は別判断

この順序なら、引継ぎを失わず、不要な一般社員向け機能だけ安全に縮小できる。
